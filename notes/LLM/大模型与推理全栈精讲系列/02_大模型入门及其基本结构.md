# 02 大模型入门及其基本结构

> [!Quote] 本篇导读
> 大模型看起来像一个会聊天、会写代码、会总结、会推理的智能系统，但在最底层，它首先是一台围绕 token 序列运行的概率机器。理解大模型，不应该从“它像不像人”开始，而应该先看清它如何把文本变成数字，把数字变成概率，再把概率一步步展开成输出。
>
> 本篇只解决一个问题：**一次现代大模型请求，到底经过了哪些核心对象、阶段和边界？** 只要这条链路稳住，后面学习 Attention、Transformer、KV cache、分布式推理、RAG 和 Agent 时，就不会把一堆术语看成彼此孤立的名词。

## 1. 大模型首先是语言模型

### 1.1 从补全游戏进入

先看一个很普通的句子：

```text
今天晚上我想吃 ___
```

人看到这个空格，可能会想到“火锅”“面条”“米饭”“烧烤”。这些候选不是完全随机的，它们受前文、语法、常识、说话习惯和场景共同约束。

语言模型做的事情，可以压缩成一句话：

**给定已经看到的 token 序列，预测下一个 token 的概率分布。**

用公式写就是：

$$
P(x_t \mid x_1, x_2, \ldots, x_{t-1})
$$

这里的 $x_t$ 不是一定等于一个汉字、一个英文单词或一个完整词语，而是一个 token。现代语言模型不会直接吐出“答案全文”，而是在每一步给出所有候选 token 的分数或概率，再由解码策略选出下一个 token。

### 1.2 为什么预测下一个 token 不简单

如果只把 next-token prediction 理解成“猜下一个字”，它会显得过于朴素。真正关键的是：为了猜得准，模型必须被训练去捕捉很多隐藏结构。

比如要补全：

```text
法国的首都是 ___
```

模型需要压缩世界知识。

再比如：

```text
如果明天下雨，我们就 ___
```

模型需要理解条件关系。

再比如：

```text
他把苹果放进篮子，然后提着它走了。这里的“它”指的是 ___
```

模型需要处理指代、上下文和常识。

因此，next-token prediction 看似是一个局部任务，实际会把模型推向更深层的语言结构学习：语法、语义、事实、格式、代码模式、推理链条、对话角色和任务约束，只要它们能降低预测损失，就会在训练压力下被压缩进模型参数。

这也是大模型能力来源中最重要的一点：**模型不是被逐条灌入规则，而是在预测任务中被迫压缩语言、知识和模式。**

### 1.3 大模型能做什么

大模型可以聊天、写作、翻译、总结、写代码、改代码、回答问题、抽取信息、生成计划、解释概念，也可以在工具系统里参与检索、调用 API 或操作环境。表面上这些任务差异很大，但从模型本体看，它们都可以回到同一件事：

```text
当前上下文 -> 候选 token 分布 -> 选择下一个 token -> 更新上下文 -> 继续
```

所谓“会总结”，是模型在“请总结以下内容”这个上下文下，逐 token 生成摘要文本；

所谓“会写代码”，是模型在函数签名、注释、已有代码和指令约束下，逐 token 生成更可能成立的代码序列；

所谓“会推理”，是模型在问题、示例、格式和已生成中间步骤的约束下，逐 token 展开一个看起来符合任务目标的推理过程。

这并不意味着所有能力都等价，也不意味着模型真的拥有可靠的事实数据库。它只说明：从底层执行机制看，大模型的各种表面能力，都要通过同一条生成链路表达出来。

## 2. “大”来自多个维度

“大语言模型”里的“大”，不是单一数字。只看参数量，会把很多关键约束藏起来。

![大语言模型的规模维度|900](imgs/llm-scale-dimensions-handdrawn-cn.png)

### 2.1 参数规模

参数是训练得到的数值，通常以矩阵和向量的形式存在。embedding table、Attention 投影矩阵、FFN 权重、输出层权重、归一化参数，都会成为模型参数的一部分。

参数越多，模型潜在表达能力越强，但它也会带来更高的训练成本、显存需求、加载成本和推理开销。一个模型不是参数越多就必然越好，参数规模必须和数据、训练目标、架构、算力预算配合。

### 2.2 数据规模与质量

模型通过训练语料学习语言模式。数据覆盖面、去重质量、领域分布、代码比例、多语言比例、指令数据质量，都会影响模型最终能力。

如果参数很多但数据不足，模型可能“装不满”；如果数据很多但模型太小，模型可能表达不下复杂模式。大模型不是把语料原文原封不动存进去，而是把大量统计规律以有损压缩的方式沉淀到参数中。

### 2.3 计算规模

训练大模型需要大量矩阵运算，推理时也要为每个生成 token 执行前向计算。训练阶段的计算规模决定了模型能否充分学习；推理阶段的计算规模决定了服务成本、延迟、吞吐和并发能力。

上一讲已经建立过 GPU 的计算直觉：算力不是抽象速度，它会直接决定模型能否训练、能否部署、能否服务更多用户、能否支持更长上下文。

### 2.4 上下文长度

上下文长度决定模型一次请求中最多能看到多少 token。它不等于模型“永久记住了更多东西”，而是决定当前推理时可以放进多少输入、历史对话、检索资料和已生成内容。

上下文变长，会改变模型能使用的现场材料，也会增加注意力计算、KV cache 占用和调度压力。因此长上下文既是能力扩展，也是系统工程问题。

### 2.5 架构与目标函数

参数、数据和算力不是孤立发挥作用。模型采用什么架构、用什么目标训练、如何组织上下文边界、是否使用 decoder-only 主干、是否引入 MoE、是否使用 GQA、RoPE、RMSNorm 等现代组件，都会影响最终能力和工程成本。

本篇暂不展开这些结构细节，只先建立一个边界：**大模型的能力来自参数、数据、计算、上下文、架构和训练目标的共同作用，而不是来自某一个神秘数字。**

## 3. 训练与推理

### 3.1 训练是在改参数

预训练可以理解为在海量文本上反复做 next-token prediction。给定一段 token 序列，训练系统会让模型预测每个位置的下一个 token，并根据真实 token 的概率计算损失。

例如用字符片段模拟 token 序列：

```text
人工 -> 智
人工智能 -> 正
人工智能正 -> 在
人工智能正在 -> 改
...
```

真实系统会以 tokenizer 产出的 token 为单位，而不是简单按字符切分。训练时，模型输出一个候选 token 分布；真实 token 概率越高，loss 越低；真实 token 概率越低，loss 越高。

常见的负对数似然损失可以写成：

$$
L = -\log P_\theta(x_t \mid x_{<t})
$$

这里的 $\theta$ 代表模型参数。训练的目标就是不断调整 $\theta$，让模型对真实下一个 token 的预测更准确。

这一步很关键：**训练阶段会更新参数。**

模型学到的语法、事实、代码模式、推理格式和表达习惯，都是在这样的训练压力中被压缩进参数的。这个压缩不是无损数据库索引，所以它会带来泛化能力，也会带来错误、偏差和幻觉。

### 3.2 推理是在用参数

推理阶段的重点不是学习参数，而是使用已经训练好的参数处理当前上下文。

系统给模型一个 prompt，模型把 prompt 变成 token 序列，经过前向计算得到下一个 token 的分布，再根据解码策略选出一个 token。这个 token 会追加回上下文，模型继续下一轮前向计算，直到遇到停止条件。

![预训练与推理的关系|900](imgs/llm-pretraining-inference-handdrawn-cn.png)

训练和推理的关系可以这样区分：

| 阶段 | 参数是否更新 | 输入对象 | 输出对象 | 核心目标 |
| --- | --- | --- | --- | --- |
| 预训练 | 是 | 大规模训练文本 | 更新后的参数 | 建立基础语言与知识能力 |
| 继续预训练 | 是 | 某类领域语料 | 更新后的参数 | 适应领域分布 |
| 有监督微调 | 是 | 指令、任务、示例答案 | 更新后的参数 | 学会任务格式和回答规范 |
| 推理 | 通常否 | 当前上下文 | 生成 token 序列 | 使用固定参数完成当前请求 |
| prompt / RAG | 通常否 | 提示词、检索资料、历史对话 | 当前上下文变化 | 改变模型此刻可见的信息 |

### 3.3 为什么这个区分重要

很多大模型系统的设计判断，都卡在“改参数”还是“改上下文”这条边界上。

如果只是想让模型回答某份文档里的内容，优先考虑检索、引用和上下文组织；

如果想让模型长期适应某个领域的表达分布，可以考虑继续预训练或领域微调；

如果想让模型遵守某种回答格式、任务规范和交互习惯，可以考虑监督微调或偏好优化；

如果只是当前任务需要临时约束，prompt、few-shot examples、system instruction 和 RAG 往往更合适。

对个人知识库尤其如此。把资料整理成可检索、可引用、可放入上下文的知识资产，通常比直接训练模型更可控、更可维护，也更容易保留来源边界。

## 4. 一次生成请求的完整数据流

现在把一次推理请求拆开看。现代 LLM 的请求不是“文本进去，答案出来”这么简单，中间会经历一条清晰的数据类型变化链。

![一次 LLM 生成请求的完整生命周期|900](imgs/llm-request-lifecycle-overview-handdrawn-cn.png)

这张图把本章最重要的边界放在同一张图里：上下文是输入材料，参数是长期权重，多层网络用参数处理当前上下文并产生 hidden state，logits 和 softmax 给出候选分布，解码策略选出 next token，再把它追加回上下文。

![大模型的 next-token 预测流水线|900](imgs/llm-basic-token-pipeline-handdrawn-cn.png)

### 4.1 文本先变成 token

神经网络不能直接计算自然语言字符，它接收的是数字张量。文本进入模型之前，需要经过 tokenizer，把原始文本切成 token，再把 token 映射成整数 id。

示意如下：

```text
输入文本：我喜欢AI
token：  我 | 喜欢 | AI
token id：2769 | 4562 | 9913
```

真实 tokenizer 可能把中文、英文、空格、标点、罕见词、代码片段切成不同粒度的子词单元。一个 token 可能是一个汉字、一个英文词、一段词根、一个空格加单词，也可能是一段符号。

这里要先排除三个误区：

- token 不等于字符；
- token 不等于自然语言里的“词”；
- context length 通常按 token 计算，而不是按字数计算；

tokenizer 的意义是让模型用有限词表处理无限变化的文本形态。尤其是 subword tokenization，它让模型可以组合表示罕见词、变量名、代码符号和新造词。

### 4.2 token id 再变成向量

token id 只是编号，编号本身没有语义距离。id 100 和 id 101 在词表中挨得近，不代表它们语义接近。

所以模型需要 embedding table，把每个 token id 映射成一个稠密向量：

$$
e_i = E[x_i]
$$

其中 $E$ 是 embedding table，$x_i$ 是第 $i$ 个 token 的 id，$e_i$ 是对应向量。

向量表示的意义在于，模型可以用连续空间表达 token 之间的相似性、组合关系和上下文变化。早期 word2vec 已经展示过，稠密向量可以承载大量语义关系。大模型继承了这个思想，但不再只学习孤立词向量，而是在深层网络中不断更新每个位置的上下文表示。

### 4.3 多层网络加工表示

embedding 进入模型后，会经过多层神经网络。每一层都接收上一层表示，并输出一组新的表示：

$$
h^{(l)} = F^{(l)}(h^{(l-1)})
$$

其中 $h^{(0)}$ 是输入 embedding，$h^{(l)}$ 是第 $l$ 层输出。经过多层加工后，每个位置都会得到一个 hidden state，也就是该位置在当前上下文下的内部表示。

现代主流 LLM 通常使用 decoder-only Transformer 作为主干。一层 Transformer block 往往包含 Attention、FFN、Residual Connection 和 Normalization 等组件：

![Transformer Block 中的 Residual、Attention 与 FFN|900](imgs/transformer-block-residual-ffn-handdrawn-cn.png)

这张图在本篇只承担占位直觉：Attention 更偏向让不同 token 位置交换信息；FFN 更偏向对每个位置的表示做非线性加工；Residual Connection 给信息和梯度提供绕行通道；Normalization 帮助深层网络保持数值稳定。完整机制会在后续 Attention 与 Transformer 篇展开。

### 4.4 hidden state 变成 logits

当最后一层输出 hidden state 后，模型仍然没有得到自然语言。自回归生成下一 token 时，通常会取最后位置的 hidden state，把它投影到词表大小的 logits：

$$
z_t = h_t W_{\text{out}} + b
$$

如果词表有 100,000 个 token，那么 logits 就是一组长度为 100,000 的未归一化分数。每个分数对应一个候选 token。

要把 logits 变成概率，需要经过 softmax：

$$
P(x_{t+1}=v_i \mid x_{\le t}) = \text{softmax}(z_t)_i = \frac{e^{z_{t,i}}}{\sum_j e^{z_{t,j}}}
$$

softmax 会让所有候选 token 的概率加起来等于 1。分数更高的候选更容易被选中，但不一定总是被选中，因为最后还要经过解码策略。

### 4.5 生成是一个回环

大模型生成回答时，不是一次性写好全文，而是自回归生成：

![LLM 自回归生成循环|900](imgs/llm-autoregressive-generation-loop-handdrawn-cn.png)

每一轮可以写成：

```text
当前上下文 -> 前向计算 -> logits -> 概率分布 -> 选出 next token -> 追加到上下文 -> 下一轮
```

如果 prompt 是：

```text
请用一句话解释语言模型：
```

模型可能先选出“语言”。下一轮上下文就变成：

```text
请用一句话解释语言模型：语言
```

再下一轮可能选出“模型”，上下文继续变成：

```text
请用一句话解释语言模型：语言模型
```

这解释了为什么生成过程会受前面输出影响：模型每一步都基于当前上下文重新计算下一步分布。前面生成的 token 一旦进入上下文，就会参与后续预测。

一次请求的生命周期可以总结为七步：

1. 准备上下文：整理 system prompt、用户输入、历史对话、RAG 片段和工具结果；
2. tokenization：把文本切成 token ids；
3. embedding：把离散 id 映射成连续向量；
4. 多层前向：每一层加工表示并产生激活；
5. 输出分布：最后位置 hidden state 映射到 logits，再变成候选 token 概率；
6. 解码：用策略选出 next token；
7. 回环：把新 token 追加回上下文，继续下一轮；

KV cache、batching、prefill / decode、量化、并行推理和调度优化，后面都会围绕这条生命周期做工程加速或资源取舍。

## 5. 参数、激活与上下文

理解大模型时，最容易混淆的是三类对象：参数、激活、上下文。它们都和“信息”有关，但生命周期完全不同。

![参数、激活与上下文的区别|900](imgs/llm-weights-activations-context-handdrawn-cn.png)

### 5.1 参数是什么

参数是模型中通过训练学出来的可调数值。它们通常长期保存在模型权重文件中，推理时加载到显存或内存里参与计算。

用符号表示，模型可以写成：

$$
f_\theta(x)
$$

其中 $\theta$ 代表全部参数。训练的过程就是不断调整 $\theta$，让模型对训练文本的预测更接近真实下一个 token。

参数有三个特点：

- 训练中会被更新；
- 推理时通常固定不变；
- 承载模型从数据中压缩出的统计规律和模式；

这也是为什么同一个模型可以离线保存、复制、加载和部署：模型权重本质上就是训练后的参数集合。

### 5.2 激活是什么

激活是一次前向计算中随当前输入产生的中间状态。它不是模型文件里长期保存的知识，而是模型处理当前上下文时临时产生的向量。

例如第 $l$ 层的表示：

$$
h^{(l)} = F^{(l)}(h^{(l-1)})
$$

这里的 $h^{(l)}$ 就是当前输入经过第 $l$ 层后的激活。换一个 prompt，激活会变化；同一个 prompt 换一层，激活也会不同。

参数和激活的关系可以这样看：

| 对象 | 是否长期保存 | 是否随输入变化 | 作用 |
| --- | --- | --- | --- |
| 参数 | 是 | 推理时通常不变 | 保存模型学到的模式 |
| 激活 | 否 | 是 | 表示当前输入在模型内部的中间状态 |

如果把模型比作一台机器，参数更像固定零件和调好的刻度，激活更像这台机器处理某个输入时临时流动的信号。

### 5.3 上下文是什么

上下文是模型当前可见的 token 序列。它可以包括用户输入、系统提示、历史对话、检索到的文档、工具返回结果，以及模型已经生成的 token。

上下文不是参数的替代品。参数是训练后保留下来的长期数值；上下文是推理时临时给模型看的输入材料。把一段资料放进 prompt，只是让模型在当前请求里能看到它，不等于把资料永久写进模型权重。

对知识库项目来说，这个区分尤其重要：

- 参数记忆是训练阶段形成的长期统计压缩；
- 上下文记忆是推理阶段临时提供的可见信息；
- RAG 本质上是在推理前把相关资料放入上下文；
- 微调或继续预训练才可能改变模型参数；

### 5.4 三者如何一起工作

一次请求中，三者会按固定关系配合：

```text
参数：决定模型如何处理输入；
上下文：决定模型当前能看到什么；
激活：决定当前上下文在模型内部被加工成什么状态；
```

模型不会脱离上下文凭空生成，也不会在普通推理中随手改写参数。它用固定参数处理当前上下文，产生激活，再由激活导出 logits 和下一个 token。

掌握这组三分法之后，可以用一句话定位很多问题：

**这是参数里是否有模式的问题，还是上下文里是否有信息的问题，还是当前激活与解码过程如何使用信息的问题？**

### 5.5 常见混淆

**“我把资料发给模型，它是不是学会了？”**

通常不是。资料进入上下文，只影响当前请求或当前会话中的推理；除非进行训练、微调、继续预训练或显式记忆写入，否则基础参数没有被更新。

**“模型为什么同一个问题有时回答不同？”**

可能是采样策略不同，也可能是上下文不同。即使参数完全一样，只要生成时不是总选概率最高 token，输出就可能变化。

**“模型为什么会忘记前文？”**

常见原因不是参数消失，而是上下文窗口有限、历史被截断，或者重要信息没有被有效写入当前 prompt。

**“模型为什么会胡说？”**

因为它输出的是概率分布上的生成结果，不是数据库查证结果。上下文不足、训练数据偏差、问题诱导、采样随机性，都可能导致错误输出。

## 6. 解码策略与请求参数

### 6.1 logits 不是最终答案

模型最后给出的 logits 只是候选 token 的未归一化分数。softmax 会把它们变成概率分布，但概率分布仍然不是最终输出。

从候选分布到具体 token，中间还有一个解码阶段。这个阶段不改变模型参数，却会显著影响输出形态。

### 6.2 选择与采样

这里要区分两个概念：

- token 选择（selection）：从候选分布中确定一个 token，强调结果是哪个；
- token 采样（sampling）：按某种随机规则从候选分布中抽取 token，强调过程允许随机性；

greedy decoding 是一种确定性选择：总是选择概率最高的 token。temperature、top-k、top-p 则属于更广义的采样控制：它们不会改变模型参数，只改变“如何从同一组 logits / 概率里选 token”。

### 6.3 常见解码策略

常见策略可以这样理解：

- greedy decoding：总是选择概率最高的 token，结果稳定，但容易单调或陷入局部模式；
- temperature sampling：调整分布的尖锐程度，temperature 越低越保守，越高越随机；
- top-k sampling：只在概率最高的前 $k$ 个候选里采样，避免低概率长尾候选干扰；
- top-p sampling：只保留累计概率达到 $p$ 的最小候选集合，也叫 nucleus sampling，候选数会随分布形状变化；

这些策略发生在 logits / probability distribution 之后。它们不是“让模型学会新知识”，而是在模型已经给出的候选分布中，用不同规则决定下一步。

### 6.4 常见请求参数

不同框架和 API 的参数名称可能不同，但常见推理参数大致可以分成几类。

控制生成长度：

- `max_tokens` 或类似参数：限制最多生成多少 token；
- stop sequences：遇到某些停止标记或字符串时结束生成；
- context length：限制输入和已生成内容合计能占用的最大 token 数；

控制随机性：

- `temperature`：调节分布平滑程度；
- `top_k`：限制候选 token 数；
- `top_p`：限制候选累计概率质量；
- `seed`：在支持的系统里让随机过程更可复现，但不等于跨平台绝对一致；

控制重复和风格：

- repetition penalty、frequency penalty、presence penalty：减少重复或鼓励引入新 token，但不同系统定义和实现不完全相同；
- system prompt、instruction、few-shot examples：通过上下文影响任务格式、语气和约束；

理解这些参数时，最重要的是不要把它们和训练参数混淆。它们通常只影响当前请求的解码和上下文，不会把知识永久写入模型权重。

## 7. 边界与心智模型

### 7.1 大模型不是数据库

很多人第一次使用大模型时，会自然地把它想成一个巨大的知识库。这个类比有一点帮助，但很容易误导。

数据库的核心动作是检索：给定查询条件，找到匹配记录。语言模型的核心动作是生成：给定上下文，计算下一个 token 的概率分布。模型参数中确实沉淀了大量统计规律和事实关联，但它们不是以可精确查表的形式存储。

这会带来两个直接后果：

- 大模型可能给出看似流畅但事实错误的内容，因为它优化的是概率预测，不是数据库一致性；
- 大模型可以组合已有模式，写出数据库里没有的表达、解释、代码和推理过程；

所以，大模型更像一个被训练出来的语言与模式生成器，而不是一个可直接替代数据库、搜索引擎或文档系统的精确存储层。

### 7.2 知识库应该补上什么

可靠的知识系统通常会把 LLM 与检索、引用、工具、结构化数据和校验流程结合起来。

对于个人知识库来说，最有价值的不是把所有笔记“训练进模型”，而是把资料整理成模型可以稳定检索、引用和放入上下文的资产：

- Markdown 笔记负责长期沉淀；
- frontmatter、标签和目录负责可检索结构；
- RAG 负责把相关资料放入当前上下文；
- LLM 负责在当前上下文内解释、重组和生成；
- 人或自动化校验负责事实边界和质量门；

这样看，大模型不是第二大脑本身，而是第二大脑的阅读器、解释器和生成接口。真正长期积累的东西，仍然应该落在可检查、可引用、可迁移的知识资产里。

### 7.3 本篇最终心智模型

本篇可以压缩成七句话。

第一，大语言模型首先是 token 序列上的概率模型，底层动作是根据上下文预测下一个 token。

第二，next-token prediction 看似简单，但会迫使模型压缩语法、语义、事实、格式、代码和推理模式。

第三，训练是在更新参数，推理是在使用固定参数处理当前上下文。

第四，一次生成请求的数据流是：文本 -> token -> embedding -> 多层前向 -> hidden state -> logits -> 解码 -> 回环。

第五，参数、激活、上下文是三类不同对象；参数长期保存，激活随输入临时产生，上下文是当前可见 token 序列。

第六，temperature、top-k、top-p 等参数改变的是解码行为，不是模型权重。

第七，大模型不是数据库。可靠系统需要把 LLM 与知识库、检索、来源引用和校验流程组合起来。

读完这一篇后，再进入模型架构演进、Attention 和 Transformer，就可以带着一个清晰问题继续：**既然大模型要在 token 序列上反复预测下一个 token，那么它内部的序列结构，究竟应该怎样设计，才能既理解长程上下文，又适合大规模并行计算？**

## 8. 参考资料

来源对应关系：tokenizer 与 subword 讨论主要参考 BPE 和 SentencePiece；next-token prediction、预训练与 scaling 直觉参考 GPT-3、Scaling Laws 与 Chinchilla；Transformer block 只作为结构占位，详细机制留给后续篇章；参数、上下文、推理边界结合语言模型教材与现代 LLM 论文脉络解释。

1. [Neural Machine Translation of Rare Words with Subword Units](https://arxiv.org/abs/1508.07909)：BPE 在神经机器翻译中的经典应用，可用于理解 subword tokenization 的动机；

6. [Training Compute-Optimal Large Language Models](https://arxiv.org/abs/2203.15556)：Chinchilla 论文，强调固定计算预算下模型规模与训练 token 数之间的权衡；

8. [Speech and Language Processing, 3rd ed. draft](https://web.stanford.edu/~jurafsky/slp3/)：Jurafsky 与 Martin 的 NLP 教材草稿，适合系统回看语言模型、n-gram、神经语言模型和序列建模基础；
